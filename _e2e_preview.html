OpenSpec 设计哲学
OpenSpec 设计哲学：为什么"流体"比"刚性"更好
核心观点：OpenSpec 的设计哲学是 Fluid、Iterative、Easy、Brownfield——用文件系统代替数据库，用使能者代替门卫，用 Markdown 代替 DSL，用增量代替全量。这种克制不是能力不足，而是刻意的设计选择。
引言
市面上不缺"规约驱动"的工具——从需求管理系统到低代码平台，它们大多有一个共同特点：刚性。你必须按步骤来，必须填完所有字段，必须在特定阶段才能做特定事情。
OpenSpec 反其道而行。它的设计哲学是四个关键词：Fluid、Iterative、Easy、Brownfield。这不是口号，而是贯穿每一行代码的设计决策。
本文从源码层面拆解这些设计哲学背后的架构权衡。

一、Fluid：文件系统即状态
[图片占位]
"刚性"工具的状态管理
传统的流程管理工具通常需要一个数据库或状态引擎来跟踪进度：任务 A 完成了吗？阶段 B 开始了吗？文档 C 审批了吗？这带来了刚性——你必须通过系统来更新状态，不能"跳步"。
OpenSpec 的做法
OpenSpec 用文件存在性来判断一个制品（Artifact）是否完成。源码中 src/core/artifact-graph/state.ts 的核心逻辑：
如果一个 artifact 的 generates 字段对应的文件存在于磁盘上 → 它就完成了
没有数据库，没有状态文件，没有 API 调用。一个 Markdown 文件存在就是存在，不存在就是不存在。
这意味着：

•你可以随时用任何编辑器创建或删除文件

•不需要"登记"或"签出"

•Git 天然就是版本控制——文件变更是可追踪的

•没有"状态不同步"的问题

为什么这是"流体"的
因为控制流反转了。不是工具告诉你"你现在应该做什么"，而是你做了什么，工具去发现。你可以跳过某个制品，可以事后补充，可以用 AI 生成也可以手写——工具只是观察者，不是管理者。
源码中的 ArtifactGraph 类（src/core/artifact-graph/graph.ts）暴露了 getReadyArtifacts() 和 getCompletedArtifacts() 方法，它们都是查询方法，不是命令方法。图形引擎不改变任何状态，它只是基于文件系统的事实回答问题。
 
二、Iterative：依赖是"使能者"，不是"门卫"
DAG 引擎的设计意图
OpenSpec 用 DAG（有向无环图）管理制品之间的依赖关系。默认的 spec-driven schema 定义了这样的依赖链：
proposal → specs → design → tasks
在传统的流程引擎中，这意味着"必须先完成 proposal 才能开始 specs"。这是门卫模式——前置条件不满足就拒绝进入。
OpenSpec 不同。它的依赖是使能者（enabler）：

•没有 proposal.md？你仍然可以手动创建 design.md

•openspec status 会告诉你哪些制品"就绪"（依赖已完成）和"阻塞"（依赖未完成）

•但它不会阻止你做任何事情

这个设计体现在 src/core/artifact-graph/instruction-loader.ts 中。当 AI 请求某个制品的指令时，系统会：

1. 检查该制品的依赖文件是否存在

2. 如果存在，把依赖文件的内容注入到指令中

3. 如果不存在，指令中会标注"以下依赖尚未完成"

注意：步骤 3 是信息性的，不是阻断性的。AI 收到这个信息后可以选择先去完成依赖，也可以选择忽略继续。
拓扑排序：Kahn 算法的选择
ArtifactGraph 使用 Kahn 算法进行拓扑排序（graph.ts）。这个算法的特点是渐进式的——每次只处理入度为 0 的节点，然后移除它，继续处理下一批。这恰好映射了"迭代"的哲学：

•你不需要一开始就知道完整路径

•每完成一个节点，新的可能性自然浮现

•循环依赖在构造阶段就被检测并拒绝（DFS 算法，schema.ts）

为什么不用严格的阶段门禁
因为在 AI 编码的实际场景中，需求是涌现的。你可能写着 proposal 发现需要修改之前的 spec，可能写着 design 发现 tasks 需要拆得更细。强制线性推进只会增加摩擦，不如让流程自然流动。

三、Easy：Markdown + CLI 的极简组合
技术选型的克制
OpenSpec 的技术栈非常克制：

•Markdown 作为规约格式——不需要学习新语言

•YAML 作为配置格式——业界通用

•CLI 作为交互方式——不依赖任何 IDE

•Commander.js 作为 CLI 框架——轻量稳定

没有 Web UI，没有数据库，没有 Docker，没有微服务。整个工具就是一个 Node.js CLI 应用。
安装即用
npm install -g @fission-ai/openspec
openspec init
两步，完成。不需要配置服务器，不需要创建账户，不需要申请 token。对比那些需要搭建一整套基础设施的"全流程管理工具"，OpenSpec 的上手成本接近于零。
为什么刻意保持简单
因为 OpenSpec 的定位是"层"，不是"平台"。它只做一件事：在人和 AI 之间建立规约层。它不应该成为开发流程的中心，不应该要求团队改变现有工具链。
这种克制在源码中随处可见：

•配置文件只有几个字段（schema、context、rules）

•内置的 schema 只有两种（spec-driven 和 workspace-planning）

•目录结构只有 specs/、changes/、changes/archive/ 三个

•CLI 命令不超过 20 个

 
四、Brownfield：增量优于全量
[图片占位]
棕地项目面临的困境
世界上绝大多数开发工作发生在已有代码库上。对于这些项目，"写一份完整的 spec"几乎是不现实的——代码库太大了，而且你无法一次性理解所有行为。
Delta Spec：增量规约设计
OpenSpec 用 Delta Spec 解决这个问题。你不是重写整个 spec，而是描述相对于当前 spec 的变更：
## ADDED Requirements

### Requirement: Dark Mode Toggle
WHEN user clicks the dark mode toggle
THEN the system SHALL switch to dark theme

## MODIFIED Requirements

### Requirement: Theme Persistence
[原有内容保留，修改部分标注]

## REMOVED Requirements

### Requirement: Light-Only Theme
[此需求将被完全移除]
源码中 src/core/specs-apply.ts 是 Delta Spec 的合并引擎，处理流程：

1. 解析（Parse）：从 delta spec 文件中提取 ADDED/MODIFIED/REMOVED/RENAMED 操作

2. 校验（Validate）：检查被修改/删除的需求是否在主 spec 中真实存在

3. 应用（Apply）：按 RENAMED → REMOVED → MODIFIED → ADDED 的顺序执行操作

4. 写回（Write）：将合并后的内容写回主 spec 文件

操作顺序不是随意的——先重命名（避免名字冲突），再删除（腾出空间），再修改（原地更新），最后添加（追加新内容）。这个顺序确保每一步都在一致的状态上执行。
为什么是"增量"
因为棕地开发本身就是增量的。你不会一次重写整个认证模块，你只会"加一个 OAuth 登录选项"或"修改密码策略"。Delta Spec 让规约的粒度和实际开发的粒度对齐——改多少，写多少。
 
五、三层解析：渐进式配置
配置层级的设计
OpenSpec 的 Schema 解析遵循三层优先级（src/core/artifact-graph/resolver.ts）：
项目级（openspec/schemas/）> 用户级（~/.config/openspec/schemas/）> 内置（包内 schemas/）
这个设计借鉴了 .npmrc 和 .gitconfig 的层级模式，但它有一个重要的语义差异：

•项目级：团队共享的工作流，提交到 Git

•用户级：个人偏好，不提交到 Git

•内置：开箱即用的默认值

这意味着：

•团队可以定义统一的工作流模板（项目级），每个人不需要单独配置

•个人可以覆盖团队的某些设置（用户级），不影响其他人

•不配置任何东西也能用（内置兜底）

为什么不只用一层
因为团队和个人有不同的需求节奏。团队需要一致性，个人需要灵活性。三层解析同时满足了两者的需求，而且用标准的文件系统路径来实现，不引入新的概念。

六、适配器模式：30+ 工具，一个接口
问题的复杂性
OpenSpec 支持 30+ AI 编码工具。每个工具有不同的：

•配置文件路径（.claude/、.cursor/、.windsurf/...）

•文件格式（SKILL.md、自定义格式...）

•命令语法（slash 命令、自然语言触发...）

源码中的解法
src/core/command-generation/ 目录实现了经典的适配器模式：
interface ToolCommandAdapter {
  getFilePath(): string;      // 这个工具的配置文件在哪
  formatFile(content): string; // 内容格式化为什么样
}
25+ 个适配器（adapters/claude.ts、adapters/cursor.ts、...）实现这个接口。一个静态注册表（registry.ts）维护工具 ID 到适配器的映射。
为什么是适配器而不是插件系统
因为 OpenSpec 不想让"支持新工具"变成一件复杂的事情。添加一个新的 AI 工具支持，只需要：

1. 创建一个新文件实现 ToolCommandAdapter 接口

2. 在注册表中注册

没有插件 API，没有生命周期管理，没有依赖注入。一个接口，一个注册，完成。
这种克制确保了系统的可扩展性和可维护性之间的平衡——足够灵活以支持新工具，又足够简单不至于引入架构复杂度。
 
七、对比：OpenSpec vs 传统方法
维度传统瀑布流敏捷看板OpenSpec

状态管理阶段门禁列（待办/进行/完成）文件存在性

AI 集成无无原生支持 30+ 工具
学习成本高（需要流程培训）中（需要工具培训）低（Markdown + CLI）

OpenSpec 不是要取代敏捷或瀑布，而是填补了一个空白：AI 编码场景下的人机协作规约。它比敏捷更结构化（AI 需要结构化的输入），比瀑布更灵活（人不应该被流程束缚）。
 
总结
OpenSpec 的设计哲学可以用一个词概括：克制。

•用文件系统代替数据库——克制复杂度

•用使能者代替门卫——克制控制

•用 Markdown 代替 DSL——克制学习成本

•用增量代替全量——克制工作量

•用适配器代替插件——克制架构

这种克制不是能力不足，而是刻意的设计选择。在 AI 编码工具爆发式增长的今天，工具的"层"越薄越好——它应该无感地融入现有工作流，而不是要求你围绕它重新组织工作。
流体胜过刚性，不是因为刚性不好，而是因为在 AI 编码的语境下，流性的成本更低、适应性更强、迭代更快。
